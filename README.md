# 웨이퍼맵 결함 분류 AI — Streamlit 데모

WM-811K 웨이퍼맵을 입력하면 세 단계(통과 / 불량 / 직접확인필요) 중 하나로 자동 판정해주는
도구입니다. 사제동행세미나 프로젝트의 최종 산출물을 로컬에서 바로 실행해볼 수 있도록 만든
Streamlit 앱입니다.

**핵심 판정(CNN 3모델 앙상블 + 트리아지)은 100% 로컬 NumPy 코드로 동작하고, LLM이나
인터넷 연결이 전혀 필요 없습니다.** 아래 2)번(배치 AI 브리핑)과 3)번(원인 Q&A 챗봇)만
Gemini API를 쓰는 선택적 부가 기능이고, API 키 없이도 1)번(단일 검사)은 그대로 씁니다.

## 실행 방법

```bash
# 1) (처음 한 번만) 필요한 패키지 설치
pip install -r requirements.txt

# 2) 앱 실행
streamlit run app.py
```

실행하면 브라우저가 자동으로 열리고 `http://localhost:8501` 에서 앱을 바로 쓸 수 있습니다.

## 사용법 (탭 4개)

### 1) 🔍 단일 검사
- 왼쪽 사이드바에서 통과/불량 판정 임계값을 조절할 수 있습니다 (기본값은 val/test set으로
  검증된 추천값, 건드리지 않아도 됩니다).
- "샘플에서 선택"으로 9가지 패턴(정상 + 8종 결함) 예시를 바로 테스트하거나, "직접 업로드"로
  본인이 가진 웨이퍼맵(.npy, 정수 0=다이없음/1=양품/2=불량 2차원 배열, 크기 무관)을 올려서
  테스트할 수 있습니다.
- 오른쪽에 판정 결과가 뜹니다 — "불량"이면 우선 점검해볼 만한 원인 후보 + **관련 공정 태그**까지
  같이 보여줍니다. "직접확인필요"로 빠진 경우에도 확률 높은 순 후보 패턴별로 관련 공정을
  참고용으로 보여줍니다(예: Edge-Loc 56% + Scratch 19% + Loc 15%로 애매하면, 세 패턴 각각의
  점검 공정을 같이 제시) — 확정은 아니지만 사람이 맨땅에서 점검을 시작하는 것보다 낫다는
  판단입니다.
- **Scratch 형태 필터** (사이드바): 9종 패턴 중 Scratch는 유독 정밀도가 약합니다 — test set
  24,703장 실측 기준, CNN이 "Scratch, 불량 확정"까지 간 59건 중 진짜 Scratch는 30건뿐이고
  나머지 29건은 다른 패턴을 잘못 본 오탐입니다(정밀도 0.51). 그래서 64×64 중간 단계에서
  불량 다이들이 실제로 "길쭉한 선 모양"인지(연결-덩어리 + PCA 길쭉함 지수) 한 번 더 확인하는
  필터를 추가했습니다. 통과 못하면 "불량" 확정이 아니라 "직접확인필요"로만 낮춥니다 —
  **절대로 "통과"로 바뀌지는 않습니다.** 사이드바 슬라이더로 엄격도를 조절할 수 있고(실측):

  | 필터 엄격도 | 정밀도 | 재현율 |
  |---|---|---|
  | 사용 안 함 | 0.51 | 0.18 |
  | 0.15 (기본값) | 0.64 | 0.15 |
  | 0.08 (엄격) | 0.77 | 0.12 |

  엄격할수록 오탐은 줄지만, 모양이 애매한 진짜 Scratch까지 같이 "직접확인필요"로 넘어가서
  재현율이 떨어집니다 — 다만 그 경우도 사람이 보게 되는 것일 뿐 "통과"로 숨겨지는 건
  아니므로, 상대적으로 안전한 트레이드오프입니다.

  **배치 분석 탭에서 필터 효과를 확인할 때 주의할 점**: "예측 패턴 분포" 차트는 CNN의
  1순위 예측(predicted_pattern)만 집계하는 차트라서, 필터를 켜고 꺼도 절대 바뀌지 않습니다
  (필터는 최종 action만 바꿀 뿐 예측 자체를 바꾸지 않기 때문 — 의도된 설계입니다). 필터
  효과는 그 위의 **통과/불량/직접확인필요 건수**와 **"불량 판정의 관련 공정 빈도"** 차트에서
  확인해야 합니다 (둘 다 최종 action이 '불량'인 것만 집계하기 때문). 또한 Scratch는 전체의
  약 0.7%뿐인 드문 패턴이라, 작은 샘플 배치에는 Scratch로 예측되는 웨이퍼가 아예 없을 수도
  있습니다 — 그러면 필터를 켜든 끄든 보일 변화가 없는 게 당연합니다(버그 아님). 지금 데모
  배치(226장)에는 이 효과를 보여주기 위해 Scratch 관련 사례를 일부러 섞어 넣었습니다.

### 2) 📦 배치 분석
- 웨이퍼맵을 한 장씩 보는 게 아니라, **여러 장을 한 번에** 돌려서 "사람이 실제로 봐야 하는 건
  전체의 몇 %뿐인지"를 보여주는 탭입니다. 실무에서 이 도구가 아끼는 시간은 한 장을 더 잘
  읽는 데서 오는 게 아니라, 대부분을 사람이 아예 안 봐도 되게 만드는 데서 옵니다.
- 직접 가진 .npy 파일 여러 개를 올리거나, **"데모 배치 불러오기"** 버튼을 누르면 실제
  test set에서 무작위로 뽑은 226장(현업과 비슷하게 대부분 정상, 일부만 결함인 분포)을
  바로 돌려볼 수 있습니다. 이 중 6장은 Scratch 형태 필터 효과를 직접 볼 수 있게 일부러 골라
  넣은 것입니다(진짜 Scratch 3장 + 오탐이었던 사례 3장) — 사이드바에서 필터를 켜고 끄면
  "불량"/"직접확인필요" 건수가 바뀌는 걸 확인할 수 있습니다.
- (API 키 설정 시) "AI 브리핑 생성" 버튼을 누르면 이번 배치의 집계 수치(통과/불량/확인필요
  건수, 패턴 분포, 공정 태그 빈도)만 보고 Gemini가 3~5문장짜리 요약을 써줍니다 — 원본
  이미지는 전혀 전송하지 않고, 이미 계산된 숫자만 보냅니다.

### 3) 💬 원인 Q&A (API 키 필요)
- "Edge-Ring 패턴은 어느 공정을 먼저 봐야 해?" 같은 자연어 질문에, `config/pattern_cause_map.json`
  지식베이스(문헌 근거 포함) **안의 내용에만 근거해서** 답하는 챗봇입니다. 근거 없는 내용은
  지어내지 않고 "지식베이스에 없다"고 답하도록 프롬프트에 명시해뒀습니다.

### 4) 📋 모니터링 (API 키 불필요)
- **감사 추적**: 단일검사/배치분석에서 나온 모든 판정이 자동으로 로컬 DB(`audit_log.sqlite3`)에
  기록됩니다 (언제/무엇을/어떤 판정으로). "직접확인필요" 건은 여기서 검토자 이름 + 최종 판단 +
  메모를 직접 입력해서 기록할 수 있습니다 — "사람이 뭘 바꿨는지"가 여기 남습니다.
- **모니터링**: 사람이 최종 판단을 모델 1순위 추천과 다르게 내린 비율("불일치율")과, 일별
  통과/불량/확인필요 추이를 보여줍니다. 통계적으로 엄밀한 drift detection은 아니고, "사람이
  모델을 자주 뒤집기 시작하면 뭔가 바뀐 신호"라는 가장 기본적인 추세 모니터링입니다 — 실제
  운영이라면 더 정교한 방법(분포 변화 검정 등)으로 교체해야 하는 부분이라는 점을 분명히
  밝혀둡니다.
- 로컬 실행에서는 DB가 계속 쌓이지만, Streamlit Community Cloud처럼 파일시스템이 재시작마다
  초기화되는 호스팅 환경에서는 장기 보존이 보장되지 않습니다 (실제 운영이라면 외부 DB로
  바꿔야 하는 부분).
- **🔁 재학습 후보 데이터**: 판정이 날 때마다 원본 웨이퍼맵도 같이 저장해두고(`audit_wafers/`,
  `.gitignore` 처리됨), "직접확인필요" 건을 사람이 검토해서 최종 라벨을 확정하면 그
  (웨이퍼맵, 확정라벨) 쌍이 자동으로 재학습 후보로 쌓입니다.

  "📋 재학습 후보 목록 보기/정리" expander에서 쌓인 건들을 하나씩 다시 열어볼 수 있고, 각
  건마다 **🔁 재확인**(검토 대기 목록으로 되돌려서 다시 확인 — 같은 사람이 다시 보든, 다른
  사람이 교차검증하든)과 **🗑️ 삭제**(원본 웨이퍼맵 파일까지 완전히 지우고 재학습 후보에서
  제외 — 판정 자체의 감사 기록은 남고 검토 확정 내용만 지워짐) 버튼이 있습니다. "이미
  재학습에 쓴 건도 같이 보기" 체크박스로 과거에 쓰인 것까지 다 볼 수도 있습니다.

  "📦 재학습용 데이터셋 만들기" 버튼으로 (아직 안 쓰인 건만) `retrain_pool.npz`를 수동으로
  내려받을 수도 있습니다. **실제 가중치 재학습은 앱 안에서 돌리지 않습니다** — CNN 1
  epoch에도 수 분이 걸려서 Streamlit 요청-응답 방식과 안 맞기 때문입니다. 대신 원본
  프로젝트(`wm811k_project`)에 스크립트를 두 개 추가했습니다:

  **왜 base/wide/deep 세 모델을 전부 재학습하는가**: "통과" 판정은 세 모델이 *모두*
  동의해야 나옵니다. 처음엔 wide 모델만 사람 교정 데이터로 재학습했는데, 그러면 재학습을
  반복할수록 wide의 결정 경계만 움직이고 base/deep은 고정돼서 "서로 독립적으로 다양한
  오류를 내는 세 모델"이 아니라 "점점 벌어지는 세 모델"이 되는 문제가 있었습니다. 그래서
  지금은 두 스크립트 모두 같은 재학습 후보 데이터로 세 모델을 같이 fine-tune하고,
  모델별 macro-F1뿐 아니라 세 모델을 합친 **앙상블 미탐지율**(진짜 불량인데 "통과"로 샌
  비율 — 가장 중요한 안전 지표)의 전/후 변화까지 계산해서 출력합니다.

  **기본으로 권장하는 방법 — 수동으로, 충분히 쌓였을 때만 돌리기** (위에서 내려받은 파일을
  직접 넘김):
  ```bash
  python3 20_retrain_from_review.py --pool /path/to/retrain_pool.npz --epochs 3
  ```
  검토 건수가 `--min_pool_size`(기본 20건) 미만이면 스크립트가 그냥 건너뛰고 이유를
  알려줍니다 — 아래 "실측으로 검증한 한계"에서 보듯 수십 건 이하로는 돌려봐도 효과가 거의
  없거나 오히려 트레이드오프만 생긴다는 게 확인됐기 때문입니다. 혼자 검토하는 프로토타입
  단계에서는 "충분히 쌓였다"를 사람이 직접 판단해서 가끔 실행하는 이 방식이, 매일 자동으로
  도는 것보다 낫습니다(아래 참고).

  **확장 시나리오 — 매일 자동으로 돌리기** (앱/DB를 직접 읽어서 Streamlit 없이 동작, Windows
  작업 스케줄러에 등록):
  ```bash
  python3 21_daily_retrain_job.py --app_dir "C:\Users\me\Desktop\wafer_qc_app"
  ```
  **지금 단계에서는 기본으로 권장하지 않습니다.** 혼자 쓰는 프로토타입에서는 하루에 쌓이는
  검토 건수가 몇 건 안 되고, 그 적은 양으로 매일 돌려봐도 효과가 거의 없거나 트레이드오프만
  생기는데, 아무도 매일 로그를 들여다보지 않으면 "아무도 안 볼 candidate를 밤마다 30분씩
  만드는" 낭비가 됩니다. 여러 명이 검토를 나눠 맡아서 하루에도 검토 건수가 꽤 쌓이는 실제
  운영 규모로 커졌을 때를 위해 남겨둔 기능입니다. 그날 새로 확정된 검토가
  `--min_pool_size`(기본 20건으로 올림) 미만이면 그냥 건너뛰고, 다 쓴 건에는 DB에
  "사용됨" 표시를 남겨서 다음 날 같은 데이터를 반복해서 오버샘플하지 않습니다. 결과 로그는
  `wm811k_project/data/processed/retrain_logs/YYYY-MM-DD.log`에 날짜별로 쌓입니다. 모델
  3개를 다 돌리다 보니 한 번 실행에 (이 샌드박스 기준) 약 30분이 걸립니다.

  그래도 이 확장 시나리오를 쓰고 싶다면, **Windows 작업 스케줄러 등록 방법:**
  1. `wm811k_project` 폴더 안에 아래 내용으로 `일일재학습.bat` 파일을 만듭니다(메모장으로
     작성 후 "모든 파일" 형식으로 저장):
     ```bat
     cd /d "%~dp0"
     python scripts\21_daily_retrain_job.py --app_dir "C:\Users\me\Desktop\wafer_qc_app"
     ```
     (`--app_dir` 경로는 실제 `wafer_qc_app` 폴더 위치로 바꿀 것)
  2. 시작 메뉴에서 "작업 스케줄러" 검색 → 실행
  3. 오른쪽 "기본 작업 만들기" 클릭 → 이름 입력(예: "웨이퍼 재학습") → 다음
  4. 트리거: "매일" 선택 → 원하는 시간(예: 새벽 3시, 아무도 앱을 안 쓸 시간) 지정
  5. 동작: "프로그램 시작" 선택 → "찾아보기"로 위에서 만든 `일일재학습.bat` 선택
  6. 마침 — 이제 매일 그 시간에 자동으로 돌고, 결과는 로그 파일로 남습니다.

  두 스크립트 모두 결과는 날짜가 찍힌 `cnn_candidate_YYYY-MM-DD.npz` /
  `cnn_wide_candidate_YYYY-MM-DD.npz` / `cnn_deep_candidate_YYYY-MM-DD.npz`(수동 실행은
  날짜 없이 `cnn_candidate.npz` 등 3개)로만 저장되고, 기존 `cnn_best.npz` /
  `cnn_wide_best.npz` / `cnn_deep_best.npz`는 건드리지 않습니다. 전/후 지표(특히 앙상블
  미탐지율)를 보고 전체적으로 나빠지지 않았다고 사람이 판단했을 때만, **세 파일을 묶어서
  같이** `wm811k_project/data/processed/`와 `wafer_qc_app/models/` 양쪽에 복사해 교체하세요
  (하나만 바꾸면 세 모델이 다시 벌어지고, `wafer_qc_app/models/`까지 바꿔야 실제 앱 판정에
  반영됩니다 — 둘은 별도 폴더입니다). 자동으로 몰래 바꿔치기하지 않는다는 원칙은 여기도
  동일합니다.

  **실측으로 검증한 한계**: 두 단계로 검증했습니다. ① (wide만 재학습했던 이전 버전으로)
  test set에서 뽑은 41건(오탐 20건+진짜 Scratch 21건)을 "사람이 검토해서 확정했다"고
  가정하고 돌렸을 때 — 전체 macro-F1 0.7644→0.7578로 소폭 하락, Scratch 재현율은
  0.360→0.453으로 개선했지만, 재학습에 전혀 쓰이지 않은 별도의 18건(완전히 못 본
  데이터)에서는 재현율이 변화 없었습니다 — 적은 데이터는 "학습에 쓴 것과 비슷한 케이스"만
  살짝 건드리고 진짜 낯선 데이터로는 일반화되지 않는다는 뜻입니다. ② 세 모델을 같이
  재학습하도록 바꾼 뒤, 실제 체크포인트·실제 test set(24,703장)으로 직접 1 epoch를
  돌려봤습니다 — 모델별 macro-F1은 base/wide/deep 모두 소폭 하락(0.733→0.732,
  0.769→0.748, 0.763→0.750, 재학습 pool이 전부 "정상" 라벨 6건이라 전체적으로 더
  보수적으로 바뀐 영향)했지만, **앙상블 미탐지율은 0.768%→0.356%로 오히려 개선**됐습니다
  (단, "통과" 건수도 14,319→11,703으로 줄어서, 안전은 좋아지고 사람이 다시 봐야 할 건은
  늘어나는 트레이드오프입니다). 두 결과 모두 — 재학습이 "오류 없이 돌아간다"가 "모든
  지표가 좋아진다"를 보장하지 않는다는 걸 실측으로 보여주는 사례이고, 그래서 스크립트가
  모델별 지표와 앙상블 미탐지율을 같이 출력해서 사람이 승격 여부를 판단하게 만든 것입니다.
  실제 효과를 보려면(그리고 이 트레이드오프의 방향을 제대로 가늠하려면) 검토 데이터가
  더 많이, 더 다양한 클래스로 쌓여야 합니다.

## Gemini API 키 설정 (2), 3) 탭에만 필요)

1. [Google AI Studio](https://aistudio.google.com)에 Google 계정으로 로그인 → "Get API key" →
   새 프로젝트를 만들고 키를 발급받습니다 (Flash 모델은 무료 티어로 충분합니다).
2. 이 폴더(`wafer_qc_app/`)에 있는 `.env.example` 파일을 복사해서 같은 위치에 **`.env`**
   라는 이름으로 저장하고, 안의 `GEMINI_API_KEY=` 뒤에 발급받은 키를 붙여넣습니다.
3. 앱을 다시 실행하면 사이드바에 "🤖 AI 부가기능 연결됨"이라고 뜹니다.

**`.env` 파일은 절대 남에게 공유하거나 이 폴더를 압축해서 보낼 때 포함시키지 마세요.**
API 키는 비밀번호와 같습니다 — 유출되면 다른 사람이 내 계정 한도로 요금을 쓸 수 있습니다.

## 참고

- 핵심 CNN 3개는 GPU/PyTorch 없이(개발 환경 제약) 순수 NumPy로 직접 구현되고 학습된
  모델입니다 — 그래서 매우 가볍습니다(전체 모델 3개 합쳐 1MB가 안 됨).
- 판정 로직(3모델 만장일치일 때만 "통과")과 임계값은 val set으로 설계하고 test set으로 최종
  검증을 마쳤습니다 (test 기준: 자동 통과율 58.0%, 미탐지율 0.77%).
- "불량" 판정에 같이 뜨는 원인 후보/공정 태그는 확정이 아니라 **우선 점검 순서를 좁혀주는
  참고용**입니다.
- AI(LLM)가 실제로 하는 일은 딱 두 군데입니다: (1) 배치 집계 숫자를 문장으로 요약, (2) 이미
  만들어둔 지식베이스 안에서 질문에 답하는 것. 패턴 분류와 통과/불량 판정 자체는 LLM이 아니라
  직접 학습시킨 CNN과, 사람이 설계한 트리아지 규칙이 합니다 — 무엇이 AI가 "읽기/요약"만
  하는 부분이고 무엇이 검증된 규칙 기반 로직인지 구분해서 설명하는 게 중요합니다.
